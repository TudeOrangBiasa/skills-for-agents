# Playbook: triage

Three modes. Ripen turns a raw issue into an agent-ready brief. Intake picks up one agent-ready issue and routes it to a build playbook. Review mode sorts the comments on an open agent PR. This playbook reuses the triage label vocabulary and the brief shape below.

Resolve the tracker and label strings from `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md` first. A missing file means you tell the user to run `/setup-repo` and stop.

Every comment posted to the tracker starts with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Ripen

Turns one raw issue (`needs-triage` or unlabeled) into an agent-ready brief. One issue per run.

1. Read the full issue (body, comments, labels, author, dates). Explore the codebase area it touches, in the project domain vocabulary.
2. Check redundancy by domain concept: an existing implementation means commenting where it lives and stopping, never a duplicate brief.
3. Verify the claim when cheap: reproduce a bug from the reporter steps, or confirm the gap for a feature. Report confirmed, failed, or insufficient detail.
4. Interview the maintainer with the Skill tool (`plan-interview`) when the request needs fleshing out, one round at a time, sharpening terms and updating `GLOSSARY.md` as decisions land.
5. Post the agent brief as a comment: summary, current behavior, desired behavior, key interfaces, acceptance criteria, out of scope, plus one type (`bug`, `feature`, `enhancement`, `deprecation`) and one `## Kompleksitas` line (Big-O in named inputs, gh calls, LLM calls).
6. A brief missing type, `Kompleksitas`, or testable acceptance is not agent-ready: label `needs-info` with one concrete question pointing at the missing section instead. Label a sufficient brief `ready-for-agent`. Never close an issue the maintainer did not ask to close.

## Intake

1. Pick one issue per run: the one the user named, else the oldest open `ready-for-agent` issue with no assignee and no open blocker. Nothing ready means report that and stop. Claim it before any work: assign it to yourself, then re-read the issue to confirm no other runner holds it; back off when another runner beat the claim. Two agents on one issue is rework.
2. Read the issue, its comments, and the latest agent brief (the Ripen shape above: summary, current and desired behavior, key interfaces, acceptance criteria, out of scope). The brief is the contract; the body and discussion are context. Restate the goal and the problem in your own words before routing, so misunderstandings surface now instead of mid-build.
3. Confirm it still holds against the current code: the behavior is not already built, the named interfaces still exist or have a clear successor, and a bug still reproduces. Already built means you comment where it lives and ask the human to close it. Never close it yourself.
4. A brief that is missing, has no testable acceptance criteria, has no type, has no `## Kompleksitas` line, or no longer matches the code is insufficient. Post triage notes (what is established, what is still needed, each question specific, pointing at the missing section), move the label from `ready-for-agent` to `needs-info`, and stop. Never implement from a guess.
5. Route a sufficient brief by its category: `bug` goes to `playbooks/bug.md`, `feature` and `enhancement` to `playbooks/feature.md`, `deprecation` to the matching flow per its brief (`bug.md` when it removes broken behavior, else `feature.md`), plus `playbooks/ui.md` for a UI ticket. A ticket collapsed from a cleared plan-map carries settled Destination and Decisions-so-far: quote them, never run a second fog interview. Carry the issue number so `playbooks/opening-a-pr.md` links it.

## Review mode

Runs on an open agent PR when the user asks you to address its review or bot comments. Classify per `../references/bot-triage.md` (fix, dismiss, ask, pass count, learned patterns); that file holds the rubric.

1. Read every unresolved review thread and bot comment on the PR, plus the PR body and diff on the current tip.
2. Classify each one before acting, then act per the reference: fix in the lowest owning PR, dismiss with a concrete reason, or ask with `needs-human` plus a `<!-- needs-human reason=ask-thread -->` marker, disarm, and continue with the next PR.
3. Verify a claim that one command can settle (rerun the cited test on the tip) before you classify it.
4. Push the fixes, keep the PR ready (never move it to draft), and report the fix, dismiss, and ask counts with the open asks listed.
