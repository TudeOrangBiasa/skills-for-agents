# Playbook: triage

Two modes. Intake picks up one agent-ready issue and routes it to a build playbook. Review mode sorts the comments on an open agent PR. This playbook reuses the `/triage` label vocabulary and brief format; it never invokes `/triage`.

Resolve the tracker and label strings from `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md` first. A missing file means you tell the user to run `/setup-meta` and stop.

Every comment posted to the tracker starts with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Intake

1. Pick one issue per run: the one the user named, else the oldest open `ready-for-agent` issue with no assignee and no open blocker. Nothing ready means report that and stop.
2. Read the issue, its comments, and the latest agent brief (the `/triage` AGENT-BRIEF.md shape: summary, current and desired behavior, key interfaces, acceptance criteria, out of scope). The brief is the contract; the body and discussion are context.
3. Confirm it still holds against the current code: the behavior is not already built, the named interfaces still exist or have a clear successor, and a bug still reproduces. Already built means you comment where it lives and ask the human to close it. Never close it yourself.
4. A brief that is missing, has no testable acceptance criteria, or no longer matches the code is insufficient. Post triage notes (what is established, what is still needed, each question specific), move the label from `ready-for-agent` to `needs-info`, and stop. Never implement from a guess.
5. Route a sufficient brief by its category: `bug` goes to `playbooks/bug.md`, `enhancement` to `playbooks/feature.md` (plus `playbooks/ui.md` for a UI ticket). Carry the issue number so `playbooks/opening-a-pr.md` links it.

## Review mode

Runs on an open agent PR when the user asks you to address its review or bot comments.

1. Read every unresolved review thread and bot comment on the PR, plus the PR body and diff on the current tip.
2. Classify each one before acting:
   - `fix`: a plausible correctness, shipped-behavior, race, or idempotency issue, or a small change that clearly reduces risk. Fix it in the lowest owning PR of the stack, reply with the commit SHA, resolve the thread.
   - `dismiss`: the current code or context proves no change is needed. Reply with the concrete reason (the invariant, the test, the upstack use), resolve the thread. "Not an issue" is not a reason.
   - `ask`: security, privacy, auth, data, migration, schema, permission boundaries, high severity, novel, or ambiguous. Ask the human, leave the thread open.
3. When in doubt, ask. Skipping a noisy style comment is cheap; skipping a real data or security bug is not.
4. Verify a claim that one command can settle (rerun the cited test on the tip) before you classify it.
5. Push the fixes, keep the PR a draft, and report the fix, dismiss, and ask counts with the open asks listed.
