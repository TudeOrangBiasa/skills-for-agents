# Playbook: opening a PR

Invoked at the end of every playbook that changes code. The PR opens ready, never as a draft. Who merges follows the risk tier per `RISK.md`: low may land on a PASS verdict, high waits for an independent PASS or PASS+NOTES verdict on the current head, then a human merges.

1. Resolve the forge and labels before the first PR operation: `docs/agents/issue-tracker.md` for the commands (GitHub `gh pr`, GitLab `glab mr`), `docs/agents/triage-labels.md` for the label strings. A missing file means you tell the user to run `/setup-meta`; until then use `gh` and the canonical role names. Keep that forge for create, edit, and view.
2. Worktree: one worktree and one branch per unit, off main. Subagents inherit it. Two workers on one branch each get their own worktree. A dirty branch with unrelated work: patch it out, open a fresh worktree, apply.
3. Gates before the first commit or push: pre-commit hooks installed (call the Skill tool with "setup-pre-commit" when the repo lacks them), the repo check command green (lint, typecheck, tests), and visual proof captured per the `pr` skill before the body is written. A red gate stops the run; never commit, push, or open around it.
4. Commits: commit liberally, then rebase into small ordered commits. Each commit is landable on its own and the order tells the story. Amend when the fix belongs in the commit just made. Use the commit format from the standards file, default Conventional Commits.
5. Title: Conventional Commits, `type(scope): subject`. Type is `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. Scope is the changed area. The subject is short and imperative, names a real symbol when one carries the change, and has no trailing period.
6. Body: the `pr` skill template (Summary, Evidence, Merge Danger). Add a `**Scope:**` line for what the PR deliberately leaves out and a `**Verification:**` line for each command actually run plus its outcome, when Evidence does not already say it. Add a `## Risk` section per `RISK.md`. End with a `## Why this way` section: two to four plain sentences on the key decision, the alternative, and why it lost, written for a developer still building experience. Keep the body under about 40 lines. Link the source issue with `Closes #N` when one exists; a PR with no issue says so.
7. Stacks: prefer five narrow PRs to one large one. The root PR targets main. Each child branch rebases onto its parent's tip and its PR targets the parent branch (`gh pr create --base <parent-branch>`). Branch from main only for independent work. Retargeting children to the trunk after a parent merges lives in `playbooks/ready-check.md` step 7.
8. Open every PR ready, never as a draft: `gh pr create` with no `--draft` flag. GitLab takes `glab mr create` with no `--draft` flag; a merge request that still opens as a draft is marked ready with `glab mr update <id> --ready`. If a PR still opens as a draft, run `gh pr ready <number>` to mark it ready. Marking ready only flips the flag; the verdict is what gates the merge. Run `gh pr view <number>` before you report its status. Landing follows the risk tier: a `risk:low` PR with an independent PASS verdict at the current head (fresh agent, never the author) is merged in this same run; a `risk:medium` PR only when every landing condition in `playbooks/ready-check.md` holds; a `risk:high` PR never merges without an independent PASS or PASS+NOTES verdict comment and a human merge (no auto-merge). On the PR, agents never add themselves as collaborator, assignee, or reviewer. This rule covers PRs only: claiming an issue by assigning it, per the Claim step in `docs/agents/issue-tracker.md`, is allowed.
9. Apply the risk label per `RISK.md` (`risk:low`, `risk:medium`, or `risk:high`, or the strings in `docs/agents/triage-labels.md`).
10. Move the linked issue's state label to `ready-for-human` once the PR is up: remove `ready-for-agent`, add `ready-for-human`. The human now owns the next step, except landed low-risk (or qualifying medium) PRs, which move straight to done with no human touch.
11. Opening a PR does not start a babysit. Post the URL and keep building until the phase or stack is done. Review comments that arrive later go through `playbooks/triage.md` review mode, and a stack waiting on CI or conflicts through `playbooks/babysit.md`, only when the user asks.
