# Playbook: hillclimb

One measurable thing, improved iteratively against a target. You own the metric and the experiment's integrity: supervise and review, delegate the attempts. A one-off fix is `bug.md` or `perf-issue.md`; this is the loop.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, never claim a win from code inspection (rule 3).

1. Ground before choosing the metric: run `how` over the target, name the workload dimensions that move the result (data size, history, state, concurrency), and pick a case reproducing the complaint. No reproducing case means fixing the repro, not hillclimbing. Then fix one metric, the direction counting as better, and a checkable stop predicate pairing a target with a floor on attempts (for example "at least 50% better than baseline and at least 10 iterations", so a lucky early win cannot end the run). Use the user's numbers when given, otherwise agree them.
2. Build the measurement harness, prove its sensitivity, then freeze it (rule 12): run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected; when the harness cannot distinguish them, revise the workload or metric. Vet the harness by rule 19 before freezing it, and make it print its error count and a count of the work done. Once frozen, one repeatable command emits the metric, sampled past the noise (median of N, never a single run). Record the baseline and a green regression gate (tests that must keep passing) before any change.
3. Open the decision log: `.scratch/whips/<run>/decisions.tsv`, one row per attempt (id, hypothesis, change, before, after, delta, tests, verdict kept or reverted, note). Read it before each attempt. It stays out of the tree. The schema is hillclimb-specific (per-attempt measurements); the filename convention follows the repo artifact contract in `docs/agents/docs-layout.md`.
4. Ground each hypothesis in the architecture model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For perf metrics, order hypotheses by the mantras in `perf-issue.md` step 2; borrow only the order, not its stop rule.
5. Loop one hypothesis per iteration: hand the change to a delegate with tight scope and review the diff rather than typing it (rule 20); fan independent hypotheses to parallel workers in separate worktrees (rule 15). Measure before and after with the frozen harness plus the regression gate. Accept only past-noise moves with a green gate, else revert in full; a tweak that only "might help" is not kept. One commit per accepted fix, staging only the files changed (never `-A`). Log the row either way. Each iteration ends in a check before the next begins (rule 4). Unattended runs use an outside scheduler tick, not a goals loop, and keep this playbook's stop rule.
6. Push past the first plateau: on a stall (several rejects in a row), pivot category, combine near-misses, re-read the source, or go more radical before concluding the hill is climbed. Correctness and simplicity outrank the number; revert a win that breaks behavior, keep a simplification holding the number (rule 1).
7. Stop on the predicate, or when remaining ideas are marginal and not worth their cost. Never relax the predicate to meet it, never quit with cheap untried hypotheses left. Stuck means surfacing it, not spinning.
8. Close via `playbooks/opening-a-pr.md`, accepted commits stacked in the order they landed.

**Reply:** metric and target, baseline to final with percent delta, iterations kept vs reverted, each accepted fix on one line, the decision log path, and the best next idea if pushed further.
