# Playbook: bug

A reported defect, reproduced first, root-caused, fixed with runtime evidence.

1. Reproduce first on the same surface the report used, driven by the project verification skill (`create-verification` output) when one exists. Reproduce it yourself; ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it will not reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires. No repro means no fix, only a diagnosis note with the closest failing signal found.
2. Trace to root cause: call the Skill tool with "diagnose". Form the candidate hypotheses, seed them with "how" over the affected subsystem and "why" for regression history, then binary-search: each pass takes the split that cuts the most remaining problem space, gets runtime evidence, eliminates. When program state is unclear, add instrumentation or logging and read it as the code runs. Be scientific: a "might help" change is a hypothesis, not a fix, so it does not ship; when evidence refutes a hypothesis, revert what it motivated. One tight feedback loop that already goes red on this bug, then ask why until the cause, not the symptom. Resist guards that silence the crash.
3. Blast radius: name the one safety fact the fix depends on (who else calls this, what data it touches) and prove it by running code. A writeup that sounds right is worthless without the run. Push each safety fact down the evidence ladder (said so, pointed at file:line, walked the bad case, ran the real code, reproduced in the app) and say where it stopped. Mark each fact proven or unproven: an empty search is still an answer, and never invent a caller. Confirm the surviving mechanism with runtime evidence before planning the fix; if the fix crosses a function boundary, "architect" first.
4. When the test path is cheap, call the Skill tool with "tdd": failing test first, then the fix, and the regression test stays. Skip the failing test only when it would be expensive, integration-heavy, or unclear; ship the smallest change the evidence justifies, nothing more.
5. Spanning workstreams means delegate per the feature throughput checkpoint, else implement directly against the brief.
6. Verify the original repro plus the new test on the real artifact, never a proxy. "Inconclusive" or wrong-surface is not a pass: flag it. Unit tests show branch behavior, not bug absence.
7. Stage the commits so the failing repro lands before the fix in git history, then unslop gate, then PR body with before/after proof of the fixed behavior (pair table plus video when motion matters), then `playbooks/opening-a-pr.md`.

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
