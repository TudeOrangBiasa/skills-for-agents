# Playbook: autopilot-full

A queue of independent PRs run to MERGED with full autonomy. One owner per PR carries build through merge; the root watches the trail, replaces stuck owners, and closes each tick with a catch-up. Route here on "autopilot this queue", "full autopilot", or a program of one PR per item where the operator wants landing, not just code.

The operator's go covers the queue's items only. Items the operator names as theirs and PRs outside the queue stop at merge-ready per `playbooks/babysit.md`, never land. A request to state the plan is not a go.

1. Spawn one owner per PR, each in its own worktree. Create the worktree with `git worktree add` before spawning: workers share no isolation of their own, so one worktree and one branch per owner keeps writers apart. Brief per section 6 (GOAL, SCOPE, CONTEXT, ACCEPTANCE, VERIFY, TIMEBOX, FORBIDDEN, REPORT, STANDING). Each owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact per the repo verification skill (built with `create-verification`), babysits to green per `playbooks/babysit.md`, and lands per `playbooks/shipping.md` once its verdict lane and merge prep clear it.
2. Open the PR early so the verifier and review bots run beside the work. The code is ready after the `no-comments` plus `unslop` plus `code-review` pass, so verification runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so the verifier runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, verifier, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks the verifier, or lands a known concurrent change to the same files, because each rebase restarts the checks. Run the repo checks for the touched paths on the committed head before the code-ready push and before a later push that needs the verifier.
3. Assume the machine dies. Soon after starting, each owner pushes and starts a decision trail per the `show-me-your-work` skill with `scripts/log.sh` in its own worktree, and pushes the trail with the work. The root records each spawned agent's id, state, and stuck-after bound in the same trail. An owner is stuck when it errors, cannot start turns, or shows no new push and no new trail row past its bound, like an owner silent by the first tick. One waiting on the root or the operator is not stuck, so answer it. Replace a stuck owner at once with a fresh agent on consolidated scope (original brief plus every later directive plus prior report and branch).
4. Run owners in parallel off trunk, never stacked, so each PR lands on its own per `playbooks/shipping.md`.
5. Verify per the risk tier, not with a separate swarm. pstack runs an independent verifier swarm before merge; this repo does not. As a deliberate deviation, this repo trusts the mode verifier plus owner self-proof on the real artifact where pstack trusts a swarm that never wrote the code. The verifier is CI on team repos and the local verifier on solo ones, each owner self-proves per principle `prove-it-works`, and only high blast radius PRs get the extra lane per `RISK.md`.
6. Merge prep: right before landing, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for the verifier when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head. When trunk changed a caller of the patch or something the patch depends on, run the patch's checks on the merge result and merge on a pass. Otherwise merge per `playbooks/shipping.md`. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
7. Run the root layer. Anything that loosens a gate, such as a raised budget, needs a verifier run and then a fresh root note, because the owner is the one who wants green. A disabled or soft-failed check always comes out, because it stops guarding every case. On the operator's go, wake on the timer or runner tick from `docs/agents/unattended.md` and audit until no delegated work is left, because long runs drift and owners stall silently. Each tick re-reads this playbook and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it. It probes every owner and judges each by its side effects (pushes, trail rows, PR state), because status text can hide a stuck child. A tick that changed something for the operator ends per the `ketchup` skill, and one that changed nothing stays quiet.
8. Stand down at once on the operator's stop. A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it; a released owner resumes per `playbooks/pickup.md`.

**Reply:** catch the operator up per the `ketchup` skill, covering each PR's state and verdict, what merged, open operator gates, and parked follow-ups, with links to each PR and the trail.
